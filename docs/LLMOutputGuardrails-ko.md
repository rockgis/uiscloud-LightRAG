# LLM 응답 품질 가드레일 개발 가이드

이 문서는 소형/양자화(AWQ, FP8) LLM을 백엔드로 쓰는 한국어 서비스에서 반복적으로 관찰된 3가지 응답 품질 문제(다국어 혼입, 근거 없는 환각, 가짜 인용마커)를 방지하는 방법을 정리합니다. `uiscloud-LightRAG`(`lightrag/operate.py`, `lightrag/prompt.py`)에서 실제로 검증한 코드를 예시로 사용하지만, **원칙과 패턴 자체는 LightRAG가 아닌 다른 RAG/LLM 서비스에도 그대로 적용 가능**하도록 일반화해서 설명합니다.

관련 문서: `docs/LiteLLMProxySetup-ko.md`(증상별 트러블슈팅, 이 문서보다 세부적), `docs/RoleSpecificLLMConfiguration-ko.md`(역할별 LLM 분리).

---

## 1. 왜 필요한가

30B급 이하 소형 모델이나 AWQ/FP8 양자화 모델은 다음 3가지 실패 모드를 보입니다. 프롬프트 지시만으로는 **완전히 방지되지 않으며**, 반드시 코드 레벨 안전장치(defense-in-depth)를 병행해야 실사용 가능한 품질이 나옵니다.

| 실패 모드 | 예시 | 발생 시점 |
|---|---|---|
| 다국어 혼입 (bleed-through) | `효율적인变更처리를`, `표준운영절часть` | 응답 생성 시점, 확률적 |
| 환각 (근거 없는 부연 설명) | "System X는 5가지 모드를 지원합니다"만 있는 원문에 각 모드별로 그럴듯한 설명을 지어냄 | 엔티티 추출 시점(그래프에 영구 저장) + 응답 생성 시점 |
| 가짜 인용마커 | 프롬프트는 `[1]`만 지시했는데 `[KG: entity_name]`, `[ref_1]` 같은 형식을 스스로 발명 | 응답 생성 시점 |

이 세 가지는 각각 **다른 대응 전략**이 필요합니다 — 아래 원칙 참고.

---

## 2. 일반 원칙 (프레임워크 무관)

### 원칙 1 — Defense-in-depth: 프롬프트 규칙 + 코드 백스톱을 항상 같이 쓴다

프롬프트에 "하지 마라"는 지시를 아무리 구체적으로 써도(부정 예시 포함) 소형 모델은 일정 확률로 위반합니다. **프롬프트 규칙 없이 코드로만 막으면** 애초에 위반 확률 자체가 높아 코드가 처리할 양이 늘고, **코드 없이 프롬프트만 쓰면** 위반이 그대로 사용자에게 노출됩니다. 둘 다 필요합니다.

- 프롬프트: "이런 형식/내용은 절대 안 됨" + **구체적인 금지 예시 1개 이상** (추상적 지시보다 예시가 훨씬 잘 통함)
- 코드: 정규식/후처리로 위반이 실제로 나왔을 때 제거하거나 정정

### 원칙 2 — "줄 전체 드롭"과 "글자 단위 서지컬 제거"를 구분해서 쓴다

garbage가 나타나는 **위치**에 따라 다른 전략을 써야 합니다.

- **줄/문단 전체가 garbage인 경우** (AWQ 모델이 max_tokens 근처에서 문자 수프를 토해내는 tail 등) → 해당 줄을 통째로 버림. 오탐 방지를 위해 "패턴 2개 이상 매칭" 같은 보수적 임계값을 둠.
- **정상적인 문단 중간에 몇 글자만 섞인 경우** (다국어 혼입 등) → 줄을 버리면 좋은 콘텐츠까지 날아가므로, **그 글자(런)만 정규식으로 잘라낸다.** 이 문서의 `_GLUED_FOREIGN_SCRIPT_PATTERN`이 이 패턴의 예시.

이 구분을 안 하고 전부 "패턴 매칭되면 줄 삭제"로 처리하면, 실사용에서 멀쩡한 문단이 자꾸 사라지는 부작용이 생깁니다 (`uiscloud-LightRAG`에서도 처음엔 이 실수를 했다가 교정한 이력이 있음 — `docs/LiteLLMProxySetup-ko.md`의 "EXAONE-style 감지 조건 변경 이력" 참고).

### 원칙 3 — 정규식은 "오탐이 절대 없는 것"부터 짠다

같은 문서 안에 **정상적인 예외 사례**가 이미 존재하는지 먼저 확인해야 합니다.

- 예: "한글에 영어가 공백 없이 붙으면 의심" → 그런데 한국어 IT 문서엔 `ITSM에`, `KPI측정목적`처럼 **대문자 약어+조사 결합**이 정상적으로 흔함. 대소문자만으로 "정상 약어"와 "치환된 일반 단어(occurrence, Operating)"를 구분할 방법이 마땅치 않다면, **차라리 자동 수정을 포기하고 별도 이슈로 문서화**하는 편이 낫습니다 (이 프로젝트에서도 실제로 이렇게 판단해 미해결로 남긴 사례가 있음 — 8절 참고).
- 반대로 "한글에 비ASCII·비한글 문자가 공백 없이 붙으면 제거"는, 정상적인 한국어 문서에서 외국 문자를 이렇게 쓰는 경우가 사실상 없기 때문에(항상 괄호/공백으로 분리) 오탐 위험이 낮아 안전하게 자동 제거할 수 있음.

**체크리스트**: 새 정규식을 추가하기 전에 "이 패턴에 매칭되는 **정상** 사례가 이 서비스의 실제 문서에 있는가?"를 먼저 확인하고, 있다면 화이트리스트를 두거나 자동수정을 포기한다.

### 원칙 4 — 재현 테스트 시 응답 캐시를 반드시 먼저 지운다

LLM 응답 캐시(쿼리+모드 키 기반)가 있는 서비스는, 코드/프롬프트를 고친 뒤 같은 질의로 재테스트하면 **캐시된 옛날 응답이 그대로 반환**되어 "고쳤는데 그대로네?"라는 착시가 생깁니다. 재현 테스트 시:
1. 질의 문구를 매번 살짝 바꾸거나
2. 캐시 파일/스토어를 초기화(`echo '{}' > kv_store_llm_response_cache.json` 류)하고 서비스 재시작

### 원칙 5 — "데이터 레벨 오염"과 "생성 레벨 오염"을 구분해서 진단한다

같은 증상(예: 응답에 이상한 문자열)이라도 원인이 다를 수 있습니다.

- **데이터 레벨**: 인덱싱(엔티티 추출) 시점에 이미 손상된 텍스트가 그래프/벡터DB에 영구 저장된 것. → **응답 후처리로는 못 고침.** 저장된 데이터 자체를 찾아서 정정(병합/이름변경/삭제)하거나 재색인해야 함.
- **생성 레벨**: 저장된 데이터는 멀쩡한데, 매 응답 생성 시 모델이 확률적으로 만들어내는 것. → 저장 데이터를 아무리 뒤져도 안 나오고, 재현율이 낮고 매번 다른 형태로 나타남(예: 오늘 세션에서 중국어 다음엔 키릴 문자로 재현됨). → 응답 후처리(원칙 2)로 대응.

**진단 방법**: 그래프 API로 관련 서브그래프를 여러 지점에서 fetch해서 노드/엣지 description에 해당 문자열이 있는지 직접 검색. 없으면 생성 레벨 문제로 결론.

## 3. 재사용 가능한 구현 패턴 3종

아래는 `lightrag/operate.py`에 실제로 구현된 코드입니다. 정규식과 적용 위치(응답 텍스트를 최종 반환하기 직전)만 그대로 가져가면 다른 프레임워크에도 이식 가능합니다.

### 패턴 A — 다국어 혼입 서지컬 제거 (원칙 2의 예시)

```python
# 한글에 공백 없이 붙은 모든 비ASCII·비한글 문자 — 소형 모델의 다국어 혼입
# 현상(중국어 变更, 키릴 часть 등)을 겨냥. 현대 한국어 문서의 정상적인
# 외국어 표기는 항상 괄호 안이거나 공백으로 분리되어 있으므로
# (예: "표준(標準)"), 붙어있는 것만 제거해도 오탐 위험이 낮음.
_GLUED_FOREIGN_SCRIPT_PATTERN = re.compile(
    r"[^\x00-\x7F가-힣㄰-㆏]+(?=[가-힣])|(?<=[가-힣])[^\x00-\x7F가-힣㄰-㆏]+"
)

# 응답 텍스트를 줄 단위로 순회하며, 한글이 있는 줄에서만 적용
if any("가" <= c <= "힣" for c in stripped):
    despurred = _GLUED_FOREIGN_SCRIPT_PATTERN.sub("", line)
    if despurred != line:
        line = despurred
```

**적용 위치**: 다른 서비스에서는 대상 언어에 맞게 정규식의 `[가-힣㄰-㆏]` 부분만 바꾸면 됩니다 (예: 일본어 서비스라면 히라가나/가타카나/한자 범위로 교체).

### 패턴 B — 가짜 인용마커 제거

```python
# 프롬프트가 지시한 인용 형식(`[n]`)이 아닌 마커
# (예: "[KG: ...]", "[ref_1]", "[ref_ids=KG:...]") 제거
_INVALID_CITATION_PATTERN = re.compile(
    r"\s*\[(?:[^\[\]]*\bref|[^\[\]]*\bKG\b)[^\[\]]*\]", re.IGNORECASE
)

body = _INVALID_CITATION_PATTERN.sub("", body)
```

**일반화 방법**: 서비스마다 프롬프트에 지시한 "유효한 인용 형식"이 다를 것이므로, 매칭 대상은 **"우리 시스템이 지시하지 않은 키워드"**(여기선 `ref`, `KG`)를 서비스에 맞게 바꿔서 사용합니다. 정규식은 대괄호 안에 그 키워드가 있으면 통째로 제거하는 방식.

### 패턴 C — 줄 전체 드롭형 garbage tail 제거 (원칙 2의 다른 예시)

`_trim_garbage_tail()`에 구현된 6가지 감지 조건 전체는 `docs/LiteLLMProxySetup-ko.md`의 "AWQ 모델별 garbage 특성 및 감지 패턴" 표를 참고하세요. 핵심 아이디어만 요약:

- exotic 문자(비ASCII·비한글·비CJK) 비율이 높고 한글 비율이 낮은 줄 → 순수 문자 수프로 판단, 드롭
- 한글이 있는 줄인데 "코드 정크 패턴"(연속 특수문자, ALL_CAPS, 붙어있는 한/영 등)이 **2개 이상** 동시 매칭 → 드롭 (1개만 매칭 시엔 오탐 위험이 커서 드롭하지 않음 — 원칙 3)

### 패턴 D — 그라운딩(환각 방지) 프롬프트 규칙 작성법

추상적 지시("사실만 답하라")보다 **구체적인 금지 패턴 예시**를 포함해야 효과가 있습니다.

```
Do NOT add generic, plausible-sounding explanations, rationale, purpose,
or use-cases for an item unless the Context explicitly states them.

Concrete example of a FORBIDDEN pattern: if the Context only says
"System X supports five modes: A, B, C, D, E" with no further detail on
each mode, do NOT write "A: performs local-scope lookup. B: performs
global-scope analysis. ..." — those per-item descriptions are invented.
The correct answer is simply "System X supports five modes: A, B, C, D, E."
```

**중요 — 인덱싱 시점에도 같은 규칙을 넣어야 함**: 응답 프롬프트에만 그라운딩 규칙을 넣으면, 이미 오염된 채로 그래프에 저장된 엔티티 설명(인덱싱 시점 환각)까지는 못 잡습니다. `entity_extraction_system_prompt`와 `summarize_entity_descriptions`(엔티티 요약/병합 프롬프트) **양쪽 다** 같은 규칙을 넣어야 재색인 시 재발을 막을 수 있습니다.

## 4. 신규 LightRAG 서비스에 적용하는 구체적 단계

이미 운영 중인 `uiscloud-LightRAG`가 아니라 **새로 띄우는 LightRAG 기반 서비스**에 이 가드레일들을 적용하는 순서입니다.

### Step 0 — 전제: LiteLLM 프록시 구성

이 가드레일들은 모델 자체의 습관(다국어 혼입, 환각, 형식 이탈)을 보정하는 것이라 **어떤 LLM 백엔드를 쓰든 적용 가능**하지만, 프록시 연결 자체가 안 되면 의미가 없으므로 먼저 확인:

```env
# .env
LLM_BINDING=openai
LLM_BINDING_HOST=http://<litellm-host>:4000/v1
LLM_BINDING_API_KEY=<해당 노드의 마스터키 — 노드마다 다를 수 있음>
LLM_MODEL=<모델명>
EMBEDDING_BINDING_HOST=http://<litellm-host>:4000/v1
EMBEDDING_BINDING_API_KEY=<마스터키>
EMBEDDING_MODEL=<임베딩 모델명>
MAX_ASYNC=1                # 소형/양자화 모델은 1~2 권장 (동시요청 시 품질 저하 사례 있음)
OPENAI_LLM_MAX_TOKENS=700  # 너무 크면 반복루프/garbage tail 발생 위험 (모델별 실측 필요)
OPENAI_LLM_EXTRA_BODY={"chat_template_kwargs": {"enable_thinking": false}, "repetition_penalty": 1.15}
```

> **주의**: LiteLLM이 `{"error":"No connected db."}`를 반환하면 보통 DB 연결 문제가 아니라 **API 키가 그 노드의 마스터키와 다름**입니다. `store_model_in_db: false`인 프록시는 마스터키가 아닌 키를 받으면 가상키 검증을 위해 DB를 조회하려다 실패합니다.

### Step 1 — `operate.py`에 가드레일 함수 이식

새 서비스가 `lightrag` 패키지를 fork/vendoring해서 쓴다면, `_trim_garbage_tail()` 근처(모듈 레벨)에 3절의 패턴 A/B를 그대로 추가하고, `_replace_references_section()`(또는 동등한 응답 후처리 지점)에서 다음 순서로 호출:

```python
body = _INVALID_CITATION_PATTERN.sub("", body)   # 1. 가짜 인용마커 제거
body = _trim_garbage_tail(body)                   # 2. garbage tail 제거 (내부에서 패턴 A도 줄 단위로 적용)
```

순서가 중요합니다 — 인용마커를 먼저 지워야 `_trim_garbage_tail()`의 패턴 매칭이 인용마커 잔해에 오염되지 않습니다.

### Step 2 — `prompt.py`에 그라운딩 규칙 이식

응답 프롬프트(`rag_response`/`naive_rag_response` 또는 동등한 프롬프트)의 "Content & Grounding" 섹션에 패턴 D 추가. **엔티티 추출 프롬프트에도 반드시 동일 규칙 추가** (Step 3에서 설명한 이유).

### Step 3 — 신규 서비스는 "인덱싱부터 새로" 시작하므로 재색인 걱정 없음

기존 `uiscloud-LightRAG`에서는 이미 인덱싱된 문서에 오염된 데이터가 있어 그래프 정리(5절)가 필요했지만, **신규 서비스는 처음부터 그라운딩 규칙이 적용된 프롬프트로 인덱싱**하므로 이 문제 자체가 원천적으로 적을 것으로 예상됩니다. 다만 사용 모델이 다르면 새로운 실패 모드가 나올 수 있으니 아래 5절 스캔 스크립트로 초기 색인 후 한 번 점검을 권장합니다.

### Step 4 — 검증 절차

1. 짧은 테스트 문서 색인 (모드별 검증에 재사용할 고정 문구 권장)
2. `hybrid`/`global`/`mix`/`naive`/`local` 5개 모드로 각각 질의 (KG를 안 쓰는 naive 모드가 상대적으로 깨끗하면, KG 저장 데이터 자체의 오염 여부를 가늠하는 참고 신호가 됨 — 원칙 5)
3. **같은 질의를 문구를 살짝 바꿔가며 3회 이상 반복** (원칙 4 — 캐시 우회 + 확률적 현상이라 1회 테스트로는 재현 안 될 수 있음)
4. 응답에 프롬프트가 지시하지 않은 인용 형식, 비ASCII 문자, 원문에 없는 부연 설명이 있는지 육안 확인

### Step 5 — 배포 파이프라인 점검 (해당되는 경우만)

CI/CD가 "빌드된 이미지 위에 별도 파일을 덮어쓰는" 방식의 핫픽스 메커니즘을 쓰고 있다면 (예: `docker cp`로 override 파일 주입), **git 커밋과 override 파일이 어긋나지 않는지 반드시 확인**하세요. `uiscloud-LightRAG` 배포 서버에서 실제로 오래된 override 파일이 매 배포마다 최신 코드를 덮어써버리는 사고가 있었습니다 (`docs/LiteLLMProxySetup-ko.md`의 "override 핫픽스 메커니즘 폐기" 참고). 가능하면 override 없이 git → 이미지 빌드만으로 배포하는 것이 안전합니다.

## 5. 그래프 데이터 오염 점검 (기존 인덱스가 있는 서비스에 적용 시)

신규 서비스라도 다른 소스에서 데이터를 이관하거나, 그라운딩 규칙 적용 전에 이미 색인한 데이터가 있다면 아래 스캔 스크립트로 점검:

```bash
curl -s "http://<server>:9621/graph/label/list" > labels.json
python3 -c "
import json, re
labels = json.load(open('labels.json'))
labels = labels if isinstance(labels, list) else labels.get('labels', labels)
patterns = [
    re.compile(r'[A-Za-z]{3,}[가-힣]'),      # 영→한 붙음
    re.compile(r'[가-힣][A-Za-z]{3,}'),      # 한→영 붙음
    re.compile(r'[가-힣]\s[a-z]{4,}'),       # 한글+공백+소문자영단어
]
for l in labels:
    if any(p.search(l) for p in patterns):
        print(l)
"
```

> 결과는 **반드시 육안으로 하나씩 확인**하세요. `ITSM에`, `KPI측정`처럼 정상적인 대문자 약어+조사 결합이 같이 걸립니다 (원칙 3).

정리용 API (LightRAG 기준, 다른 프레임워크는 동등 기능을 찾아 대체):

| 상황 | 엔드포인트 |
|---|---|
| 오염된 이름의 정상 버전이 이미 존재 | `POST /graph/entities/merge` |
| 정상 버전이 아직 없음 | `POST /graph/entity/edit` (`allow_rename: true`) |
| 관계 0개인 내용 없는 정크 엔티티 | `DELETE /documents/delete_entity` |

병합 시 여러 출처의 `description`이 이어붙는 방식이라, **엔티티 이름은 깨끗해져도 description 안의 원문 오염 텍스트는 남습니다.** 완전히 고치려면 해당 문서를 재색인해야 합니다.

## 6. 적용 체크리스트 (신규 서비스용)

- [ ] LiteLLM 프록시 연결 확인, API 키가 해당 노드 전용 마스터키인지 확인
- [ ] `_GLUED_FOREIGN_SCRIPT_PATTERN` 이식 (대상 언어에 맞게 문자 범위 조정)
- [ ] `_INVALID_CITATION_PATTERN` 이식 (프롬프트가 지시하는 실제 인용 형식에 맞게 키워드 조정)
- [ ] 응답 프롬프트 + 엔티티 추출 프롬프트 양쪽에 그라운딩 규칙 추가 (한쪽만 하면 인덱싱 시점 환각을 못 잡음)
- [ ] 응답 후처리 호출 순서: 인용마커 제거 → garbage tail 제거
- [ ] 초기 색인 후 그래프 라벨 스캔 1회 실행
- [ ] 5개 쿼리 모드 × 문구를 바꾼 3회 반복 테스트, 캐시 초기화 확인
- [ ] CI/CD에 override류 핫픽스 메커니즘이 있다면 최신 커밋과 어긋나지 않는지 확인

## 7. 이 가드레일들이 다루지 않는 범위 (한계)

- **패턴 A/B는 "형식적으로 명백한" 위반만 제거합니다.** 문법적으로 자연스러운 문장 안에 섞인 영어 단어 치환(예: "위험 occurrence를" — "발생" 대신 영어 단어 사용)은 정상적인 대문자 약어 표기와 정규식으로 구분이 어려워 **자동으로 못 막습니다.** 이런 경우는 무리하게 정규식을 만들기보다:
  - 프롬프트 부정 예시를 계속 보강하거나
  - 생성 파라미터(`repetition_penalty`, `temperature`) 조정을 시도하거나
  - 화이트리스트 기반 정규식(그 서비스 문서에 실제 등장하는 정상 약어 목록 관리)을 별도로 구축하거나
  - 모델 자체를 교체 검토하는 것이 더 현실적입니다.
- **패턴 D(그라운딩 규칙)는 확률을 낮출 뿐 100% 방지하지 못합니다.** 소형 모델일수록 지시 준수율이 낮으므로, 중요한 응답에는 여전히 사람의 검수나 별도 팩트체크 단계를 권장합니다.
